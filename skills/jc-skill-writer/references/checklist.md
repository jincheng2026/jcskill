# 写 skill 对照清单（固化层）

> 来源：dbskill v2.14.2 全量拆解（21 个 skill）+ jc 系列模式。每条都标了检测方法和「没做到时长什么样」。
> 用法：写 skill 时按工序逐节对照；不是每条都适用——状态管理、升档闸门等只在对应 genre 才检查。
> 注意：本清单只收可检查的条目。如果你想往里加一条但写不出它的检测方法，不要加。

## 工序 0：动笔前

### 0.1 判断力的原料在哪
skill 的判断力来自真实语料的压缩（dbskill：12307 条推文→4176 条溯源原子→公理），不是凭空写的。
- 检测：随机抽 skill 里 3 条具体规则，问「这条判断从哪来」。答不上来源（用户的实战经验、参考范例、踩过的坑、真实语料）的规则就是编的。
- 没做到的样子：checklist 里全是「要清晰」「要准确」这类谁都能写、谁都没法验证的句子。
- 操作：动笔前先问用户要原料——他验证过的做法、踩过的坑、看过的好例子。原料不足时缩小 skill 范围，不要拿模板填。

### 0.2 先定 genre，再看范例
路由型、诊断对话型、状态管理型、工程脚手架型、公式库型……不同 genre 的正确写法互相冲突（如逐题问 vs 合并问）。
- 检测：能一句话说出这个 skill 属于哪个 genre、参考哪个范例。
- 操作：定下 genre 后去读 `exemplar-index.md` 对应条目和范例原文，不要凭印象写。

### 0.3 平台决定拆不拆 references
- 只跑 Claude Code：SKILL.md 做路由，细节下沉 references/，每个文件标「何时读」。
- 要跨平台分发（Codex/Cursor/Trae 等不保证读 references 的宿主）：SKILL.md 自包含，内联案例，长就长。
- 检测：问一句「这个 skill 会被分发到哪」。没问就默认拆 references 的，跨平台时会变成只剩骨架。

### 0.4 入口处写「不处理什么」
- 检测：SKILL.md 里有明确的范围外清单和劝退话术（dbs-content-system 开头直接列「不处理：单篇润色、标题优化」）。
- 没做到的样子：用户拿不适合的需求触发 skill，skill 硬着头皮空转一轮。

## 工序 1：description（最值钱也最容易写废的字段）

### 1.1 四件套齐全
功能一句话 + 中文触发词（用户原话同义词穷举，不是功能描述）+ 英文镜像触发词 + 触发边界（什么情况不该触发）。
- 检测：写完后拿 3 句用户真实会说的话（含口语、错别字变体）自测：「这句话能命中吗？」再拿 1 句相邻场景的话测：「这句不该命中，会误触吗？」
- 没做到的样子：description 只写了「分析文章结构并生成配图」——用户说「给我的文章配几张图」时不命中，因为没有一个词重叠。

### 1.2 与相近 skill 划清边界
本机已装上百 skill 时，触发冲突比触发遗漏更常见。
- 检测：description 里有「与 X 的区别：……」或「不要在 Y 场景触发」（jc-clarifier 范例：「与 BROK 优化器的区别：它假设需求半成型，本 skill 解决更上游的问题」）。
- 操作：写之前 `ls ~/.claude/skills/` 扫一遍邻近功能的 skill。

## 工序 2：身份与判断力定调

### 2.1 否定式身份开场
「你是 X。你不做 A，只做 B。」一句话锁死行为边界（dbs 路由：「你不做诊断，不做分析，只做路由」；dbs-xhs-title：「你是公式匹配器，不是标题生成器」）。
- 检测：身份段里有至少一个「不做」。
- 没做到的样子：「你是一个专业的 XX 助手」——模型该克制的地方全靠运气。

### 2.2 公理坐标系
3-6 条可引用、可否证的公理，所有具体规则从公理推导（dbskill 21 个 skill 里至少 8 个采用）。这是防模板空壳的核心。
- 检测：每条公理能回答「违反它的产出长什么样」。「想清楚再动手效率最高」是公理（违反 = 上来就输出 90% 废品）；「保持专业」不是（违反长什么样？说不出）。
- 操作：规则和公理对不上号的，要么补公理，要么删规则。

### 2.3 判断术语要么定义要么给操作测试
- 检测：grep skill 里的判断性术语（「空转」「AI 味」「复利」），每个都有定义或现场测试法（dbs-diagnosis 的空转词测试：去掉该词句子还成立 = 空转）。
- 没做到的样子：dbskill 的「hard to vary」反复出现但从不解释，假设读者懂 Deutsch——换个模型执行就跑偏。

### 2.4 正反示例对照
关键判断点配「好的：…… / 差的：……」实例对，反例带诊断要点（标准配置 3 正 2 反）。
- 检测：抽一条规则，看有没有至少一个反例展示「做错了长什么样」。
- 没做到的样子：框架不演示——dbs-deconstruct 提了「7 张表」但全文没一个完整使用案例，框架成了装饰。

## 工序 3：流程与节奏

### 3.1 Phase 化 + 显式交互闸门
每个 Phase 写清进入条件、做什么、何时必须停下等用户。节奏写成禁令，不靠模型自觉：「每做完一项就停下来等回应，不要一次性跑完」。
- 检测：找出流程里所有该停的点，每个点都有原话级禁令。
- 没做到的样子：用户要一份诊断，模型一口气跑完诊断+方案+实施清单，中间该确认的全跳过。

### 3.2 逐题问 vs 合并问，按依赖关系定
每一问依赖上一答（诊断流）→ 逐题问；问题相互独立（澄清漏斗）→ 合并问 + 选项降低回答成本。
- 检测：看相邻两问之间有没有信息依赖。两种都对，选错才错。

### 3.3 行动锁
产出类 skill 必须有「用户确认理解之前，禁止生成成品」的铁律 + 例外通道（用户两次明确说「直接做」才放行）。
- 检测：SKILL.md 里有「确认前禁止……」字样和例外处理。

### 3.4 阈值分级代替二值判断
🔴 强信号 / ⚠️ 中信号 / 💡 弱信号，每级映射不同行动；或计分制（dbs-good-question：五项各 0-2 分，0-4 / 5-7 / 8-10 三条处理路径）。
- 检测：判断环节的输出是分级 + 对应动作，不是「好/不好」。

### 3.5 拒绝权
用户关键信息全答不上时，skill 直接说明无法产出（dbs-goal：「你脑子里还没有目标，只有一团感觉」），不硬输出。
- 检测：SKILL.md 定义了「什么情况下不产出、说什么」。
- 没做到的样子：素材为零也硬生成一版，用户拿到一篇看似完整实则全是猜的东西。

### 3.6 降级执行 + 风险声明
找不到前置状态、格式损坏时不硬卡流程：用户明确要求继续 → 可以做，但开头声明「本次基于当前可见上下文生成」。写入严验证，读取宽容错。
- 检测：每个「依赖外部状态」的步骤都有找不到时的降级路径。

### 3.7 硬升档闸门（工程型 / 批量型必查）
分档运行（审计→样本→批量→全量），每次升档有可检验硬条件清单，少一条不升档（dbs-content-system：「连续 2 个批次没改字段规范」「人工抽查 30 个单元重大误判 ≤3」）。
- 没做到的样子：AI 第一轮就对 2000 个文件跑全量改写，错一处错一片。

### 3.8 完成态定义
连续型 / 长流程 skill 必须定义「什么时候算完」。
- 检测：能回答「这个 skill 的终局是什么」。dbs-learning 只有「继续下一篇」没有终局，是反例。

## 工序 4：话术与禁令

### 4.1 检测三件套
每个判断环节配齐：检测方法 + 2-3 个真实示例（含反例）+ 带 {占位符} 的话术模板。模型抄话术比理解原则可靠。
- 检测：关键交互点都有可直接抄的引用块话术。

### 4.2 禁令写到原话级
禁的是可检查的字面表达：「不要说『每个人的情况不同』」「不要用『赛道』这个词」；进阶是禁用句式清单（dbs-learning 禁「不是……而是……」「真正的……是……」）。
- 检测：每条禁令都能用 grep 或肉眼直接核查产出有没有违反。
- 没做到的样子：「避免 AI 味」——模型点头称是，照犯不误。

### 4.3 边界情况显式处理
多需求混杂、超出能力范围、用户说「不知道」、中途改方向——各配固定处理话术。
- 检测：对照 jc-clarifier「边界场景处理」一节的 5 类，至少覆盖本 skill 会遇到的那几类。

### 4.4 跨 skill 推荐要有频率约束和优先级
「触发条件 → 推荐话术」表 + 「同一信号最多提一次」；多条同时命中时写明先走哪个（dbskill 没写优先级，是它的缺陷）。

## 工序 5：状态与文件（状态管理型 genre 必查，其他略读）

### 5.1 路径决策树
用户指定 > 项目目录（以 .git/package.json 等标志判定）> 兜底目录。渐进后备，不写死。

### 5.2 持久化纪律
- 永不覆盖：时间戳即版本，修正用 `[修正 YYYY-MM-DD]` 追加。
- frontmatter schema 字段齐全且每个字段有「谁填、谁查」——有字段没人填没人查的是幽灵字段，删掉。
- 来源标签强制：`[本人]` / `[AI 推测]` / `[AI 结论]`。
- 排序用文件名时间戳前缀，不信 mtime（iCloud 会改写）。
- 时间戳用 python3 取 ISO 8601 带时区，不让模型编。

### 5.3 状态传递不抢路由
存档写 next_skill 只是技术建议；恢复后问开放问句，用户明确说继续才路由，路由时把存档内容作为上下文注入，不让用户再讲一遍。

### 5.4 模板行与用户输入硬区分
读取用户填写区时必须忽略 AI 自己写的模板提示行，只有用户新增文字算真实输入。

### 5.5 敏感信息前置确认
写入前问，不要写完才提醒「可手动删除敏感内容」（dbskill 反例：提醒后置）。

## 工序 6：收尾自检

### 6.1 references 分层 + 读取时机表
SKILL.md 末尾给「文件 | 何时读取」两列表，每个 references 文件都被指到，且时机具体（「启动时必读」「匹配场景时读」「遇到边界情况时读」）。
- 没做到的样子：references/ 里躺着没人引用的孤儿文件，或 SKILL.md 说「详见 references」但不说何时读。

### 6.2 验收命令必须真的能跑
skill 承诺的检查（lint、frontmatter 校验、脚本）逐条列出且逐条跑过。
- 检测：把验收清单里的命令真的执行一遍。dbskill 的 CI 只校验版本号不 lint frontmatter，是反例。

### 6.3 资产外化
skill 的输出设计朝「手里留下什么可复用的东西」收敛：整理好的库、验证过的模板是资产，「心里有数了」不是。
- 检测：能回答「用户用完这个 skill，磁盘上多了什么」。

### 6.4 区分方法与作者私货
- 检测：验收标准里有没有写死只适用于原作者的内容（dbskill 反例：写死 dontbesilent 自己的 5 类题材）。换个用户还成立的才进 skill。

### 6.5 自我检验
写 skill 的 skill 产出的 skill，本身也要过这份清单——尤其 1.1（拿用户原话测触发）、2.2（公理可否证）、4.2（禁令原话级）三条。
