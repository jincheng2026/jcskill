# 审查模式诊断清单

> 用法：审查现有 skill 时按本清单逐项检测，输出诊断报告（格式见文末），**经用户确认后才动手改**。
> 诊断必须具体到位置和原文引用——「description 第 3 行只有功能描述没有触发词」是诊断，「description 可以优化」不是。

## 诊断顺序

第一眼看 description（决定这个 skill 会不会被触发），第二眼扫不可执行的废话（决定触发后有没有用），然后才进入逐项检测。一个 description 写废的 skill，其他写得再好用户也见不到。

## 三大死穴（先查，命中即 🔴）

### D1. 触发不准
- 检测：拿 3 句用户会说的原话测 description 命中；拿 1 句相邻场景的话测误触。
- 病灶：description 只写功能不写触发词（「分析文章结构并生成配图」——用户说「给文章配几张图」无一词命中）；或触发词太宽抢了别家 skill 的活。
- 修复方向：补中文原话同义词穷举 + 英文镜像 + 「不要在 X 场景触发」边界 + 与相近 skill 的区别声明。

### D2. 模板化空壳
- 检测：随机抽 3 条规则问「违反它的产出长什么样」；grep「确保」「保持」「高质量」「专业」等词。
- 病灶：结构齐全（H2 标题一应俱全）但句句是「保持输出高质量」「确保准确性」——模型读完和没读一样。
- 修复方向：要么补原料（用户实战经验、范例、反例）把空话换成可检查的判断，要么承认没原料、缩小 skill 范围。

### D3. 臃肿不拆分
- 检测：`wc -l SKILL.md`；先问「这个 skill 跨平台分发吗」——跨平台自包含不算病，只跑 Claude Code 的超长主文件才算。
- 病灶：只跑 Claude Code 的 SKILL.md 塞几千字案例和模板，每次触发全量进上下文。
- 修复方向：主文件只留决策逻辑和读取指令，案例/模板/题库下沉 references/ 并标注「何时读」。

## 逐项病灶清单（dbskill 实测踩坑 + checklist 反向）

| # | 病灶 | 检测方法 | 严重度 |
|---|------|---------|--------|
| P1 | 幽灵字段：模板里有字段但没有任何流程填它、验收也不查 | 逐字段问「谁填、谁查」，答不上即幽灵 | ⚠️ |
| P2 | 框架不演示：提了框架/表格/方法但全文无完整使用案例 | 每个框架名搜配套案例 | 🔴 |
| P3 | 术语未定义:判断性术语既无定义也无操作测试 | 列出所有判断词逐个核查 | ⚠️ |
| P4 | 个人私货硬编码：验收标准写死原作者场景，换人失效 | 问「换个用户这条还成立吗」 | ⚠️ |
| P5 | 规则算法不完整：文件名/slug/格式转换规则缺边界情况（中文、连续非法字符） | 拿边界输入跑一遍规则 | ⚠️ |
| P6 | 触发条件重叠无优先级：多条推荐/路由同时命中不知先走哪个 | 构造一个多命中输入 | ⚠️ |
| P7 | 时机词模糊：「对话结束时」「适时」这类不可操作的时机定义 | 问「具体哪个事件发生时」 | ⚠️ |
| P8 | 路由无失败兜底：指向的 skill/文件不存在时没有回退 | 假设目标拼错或已删，看流程走向 | ⚠️ |
| P9 | 敏感信息提醒后置：写完文件才提醒可删敏感内容 | 找所有写盘动作，看确认在前还是在后 | 🔴 |
| P10 | 无完成态：连续型 skill 只有「继续下一个」没有终局定义 | 问「什么时候算完」 | ⚠️ |
| P11 | 验收命令没跑过：承诺的检查命令实际跑不通 | 逐条执行验收命令 | 🔴 |
| P12 | 该停不停：流程里缺交互闸门，模型一口气跑完该分步确认的事 | 找出所有产出节点，看前面有无确认禁令 | 🔴 |
| P13 | 禁令不可检查：「避免 AI 味」这类无法核查的禁令 | 每条禁令问「怎么验证违反了」 | ⚠️ |
| P14 | 孤儿 references：文件存在但 SKILL.md 没引用，或引用了不说何时读 | 对照 references/ 目录与主文件引用表 | 💡 |
| P15 | 无拒绝权：输入完全不满足前提也硬产出 | 喂一个空心需求看它接不接 | ⚠️ |
| P16 | 状态文件覆盖式更新：直接重写历史而非追加修正 | 看写文件的动词是覆盖还是追加 | ⚠️ |

严重度含义：🔴 直接影响能不能用（触发、安全、闸门）；⚠️ 影响执行质量和可迁移性；💡 整洁度问题。

## 诊断报告输出格式

```
## skill 诊断：{skill 名}

**一句话结论**：{能用但触发会漏 / 触发正常但内容空壳 / ……}

### 🔴 必须修
1. {病灶编号 + 位置（行号或小节）+ 原文引用 + 为什么是问题 + 修复方向}

### ⚠️ 建议修
…（同上格式）

### 💡 可选
…

### 没问题的部分
{一两句，说明哪些写得好不要动——防止改的时候把优点改没了}

确认后我按清单逐条改，改完逐条对照验证。
```

## 改造纪律

- 先报告，经确认再改；改之前备份原文件到同目录 `.bak` 或 `.trash/`。
- 只改诊断清单里列过的项，不顺手重构没诊断过的部分。
- 改完逐条回到检测方法验证（D1 改完重新拿 3 句原话测触发）。
