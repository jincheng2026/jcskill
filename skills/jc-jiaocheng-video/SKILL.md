# 教程视频共创

## 目标

把复杂的 AI 能力翻译成普通观众能感知的价值。第一目标是让观众产生明确的收获感，并愿意相信、收藏、关注或继续探索；「完整教会」不是默认目标，只在深度教程中提高权重。

本 Skill 处理两种短视频：教程（带操作演示）和观点口播（不带演示，用户调用前会说明是哪一种）。不承担长篇操作手册、剪辑或渲染。两种共用叙事确认、工作稿、改稿日志、反馈记录和发布前评审；差别见「教程与口播分支」。剪辑不在范围内，但写稿时必须考虑最终成片；剪辑暴露出的口播与画面对不上、素材缺口或制作成本问题，也算写稿反馈。

## 这些地方停下等你

AI 能做的尽量做，但下面这些由你判断。到了这一步，AI 把要你判断的东西摆清楚，然后停下等你，不替你拍板。

| 环节 | 你要判断什么 | 你判断之前 AI 做什么 |
| --- | --- | --- |
| 定叙事 | 拍给谁、观众看完得到什么、用什么证明、哪些不讲、你最想表达的判断、实际制作条件（时长、已有录屏、能不能补录）。你明确说「确认」「按这个来」或同义的话，才写全稿；「差不多」「再想想」不算 | 先给推荐方案和候选答案，不让你空想 |
| 先写三段 | 开头、最需要你判断的一段、结尾，方向对不对 | 只写这三段；方向通过后才补齐全稿 |
| 每轮改稿 | 哪些修改要、哪些不要 | 每轮给完整的当前版本，标出改了哪里，记进改稿日志 |
| 定稿 | 这一版就是要拍的版本 | 你确认后才存 `定稿.md` |
| 标题、封面文字、简介 | 从候选里挑 | 一次出齐候选，不借机改逐字稿 |
| 发布前评审 | 结论是「暂缓发布」时，发不发、怎么改由你定 | 说清唯一的阻断原因和怎样才能解除 |
| 写进判断库或口气样本 | 每一条同不同意写进去 | 整理成清单，先查重，把库里原文和候选并排摆出来 |
| 改本 Skill | 改不改、怎么改 | 只提一处精确的修改，并给出多条真实内容里的证据 |

## 先找到工作文件夹

你的选题、草稿、素材都放在「工作文件夹」里（和创作工作台 jincheng-workbench 用的是同一个）。每次开工先找到它，按顺序找，找到就停：

1. 这个对话打开的文件夹，或者它往上几层，里面有 `内容草稿/` 或 `选题库/00_选题总览.md`。
2. 装了创作工作台：`~/Library/Application Support/jincheng-workbench/config.json` 里的 `workFolder`（`~` 开头的换成家目录）。
3. `~/Documents/jincheng-workbench/` 存在。

都没有：用总入口 `jc` 的建文件夹脚本建好（和本 Skill 装在同一个地方，`<本 Skill 目录>/../jc/scripts/init_workfolder.py`，运行 `python3 <这个路径>`，它只补缺的、不覆盖），告诉用户一句建在哪。找不到 `jc` 时，只在 `~/Documents/jincheng-workbench/` 下建本 Skill 要用的那几个文件夹：`内容草稿/`、`写稿方法/`（`选题库/`、`已发布/` 只读，没有就跳过）。

本 Skill 在工作文件夹里用到的位置：

| 放什么 | 位置 |
| --- | --- |
| 这条内容发出去之前的全部东西 | `内容草稿/T001_选题名/`：`参考拆解.md`、`工作稿.md`、`改稿日志.md`、`版本/`、`定稿.md`、`画面规划.md`（创作页 `T001_创作页.html` 由 jc-gongzuotai-write 生成） |
| 选题卡（看这条讲什么、拍给谁、参考链接） | `选题库/<类型>/待做/T001_选题名.md`，总表 `选题库/00_选题总览.md` |
| 你的判断库 | `写稿方法/07_我的判断库.md` |
| 你的口气样本 | `写稿方法/08_我的口气样本.md` |
| 创作工作台自带的写稿方法 | `写稿方法/01_写稿流程.md` 到 `06_改稿建议怎么给.md`（装了工作台才有） |
| 你攒的爆款开头（可选） | `写稿方法/爆款开头.md` |
| 写稿反馈记录 | `写稿方法/反馈记录.md` |
| 已发布的同类视频数据 | `已发布/00_已发布总览.md`、`已发布/YYYY-MM-DD-标题/内容.md` |

## 你自己的写稿方法：判断库和口气样本

本 Skill 自带一套能独立跑完的基本做法（下面的硬规则、工作流和 [`references/baseline-model.md`](references/baseline-model.md)）。你自己攒下的东西放在工作文件夹的 `写稿方法/` 里，AI 按阶段读，让稿子越来越像你：

- `写稿方法/07_我的判断库.md`：你同意过的写稿判断。每条写「遇到什么情况 → 你怎么判断、当时为什么、出自哪条内容、什么时候不适用」。只记你同意过的；AI 自己的归纳没经你同意不进这里。
- `写稿方法/08_我的口气样本.md`：你发出去、数据好的同类终稿，和你亲手改过的句子（改前 → 改后）。怎么攒见 [`references/口气样本怎么攒.md`](references/口气样本怎么攒.md)。
- `写稿方法/01_写稿流程.md` 到 `06_改稿建议怎么给.md`：创作工作台自带的写稿方法，装了工作台才有，有就读。
- `写稿方法/爆款开头.md`：可选。你让 AI 存下来的参考开头。

**这些文件缺了照样写。** 文件不存在、只有标题、或者只写着「待填」，都算空的：按本 Skill 自带的基本做法写，并在开工时告诉用户一次，例如「你的判断库和口气样本还是空的，这次按基本做法来；写完我把你改过的句子整理出来，你同意的再存进口气样本。」只说一次，不反复提醒，不因此停下。

**按阶段读，不整库读。** 先确定现在在哪个阶段，再读会改变当前决定的那几条。判断库条目多时，先用 `rg -n` 搜和当前阶段相关的关键词，只读命中的条目。

| 当前阶段 | 判断库里读哪类条目 | 装了创作工作台时再读 |
| --- | --- | --- |
| 参考与叙事 | 受众、选题角度、参考怎么取舍、事实核查 | `01_写稿流程.md`、`03_拆参考怎么拆.md`、`04_定叙事.md` |
| 开头 | 开头怎么写（另可看 `爆款开头.md`） | `05_口播通用写法.md` |
| 正文与演示 | 正文结构、演示、证据 | `05_口播通用写法.md` |
| 结尾与承接 | 结尾、引导关注或领取资料 | `05_口播通用写法.md` |
| 改稿 | 改稿相关 | `06_改稿建议怎么给.md` |
| 交付物与画面 | 画面、录屏、资料包 | 不读 |
| 终审与发布 | 标题封面简介、平台、事实 | 不读新的，避免重新发散 |
| 反馈与复盘 | 按实际问题读 | 不读 |

口气样本只在第 3 步写稿前读一次（见第 3 步）。

**冲突时按这个顺序：** 当前真实材料和用户本轮明确确认的内容 → 本 Skill 的硬规则和工作流 → 你的判断库和创作工作台的写稿方法 → 参考视频里别人的写法（只作参考）。后两层和本 Skill 冲突时直接不用；只有不同选择会明显改变这条视频时，才把具体冲突摆给用户判断。没有命中的条目也继续写，不为了套某条写法去改叙事、事实或制作条件。

## 硬规则

1. **先确认叙事，再写完整脚本。** 用户没明确确认当前叙事前，只讨论方向，不输出完整逐字稿。
2. **每条视频不写需求文档，也不让用户填表。** 日常生产只在聊天中简短确认叙事。
3. **参考拆解和写稿分开。** 参考视频先由 `jc-video-analysis` 完整拆解；本 Skill 承接结果，只补会改变用户叙事或拍摄方案的关键缺口，不从头拆第二遍。
4. **确认后分阶段直接推进。** 不反复索要「继续」，也不在叙事确认后一次生成逐字稿、标题、封面、简介和教程。
5. **收获感优先。** 不拿「能否完整复现」取代内容价值。
6. **正片交付价值，同时保留钩子。** 可以用完整提示词、模板、检查表和扩展示例承接引流，但不能把核心价值全藏进资料包。
7. **证据优先于已确认的叙事。** 核心结果不成立或前提发生实质变化时，立即回到叙事讨论。
8. **确认过的内容不重新发散。** 除非用户重新打开或事实发生冲突，不改已确认原文，不再提供平行版本。
9. **反馈保留证据，不把审核工作推回给用户。** 保留用户原话、实际修改和结果；AI 可以根据多次实践自己归纳，但必须标清「用户原话」和「AI 归纳」。只有证据冲突、且不同选择会明显改变产出时才请用户判断。
10. **标题、封面、简介和教程不得暗改逐字稿。** 它们分别确认，始终以当前确认稿为依据。
11. **先分平台，再定承接。** 不把同一套引导动作（CTA）复制到所有平台。小红书不得要求观众评论关键词；视频和发布配文不给这类动作指令，发布后可以由作者在评论区自然说明教程已放进粉丝群、大家自取。
12. **发布前必须轻量评审。** 不打分、不建状态流转，只拦截会伤害理解、真实性、交付或平台合规的问题；细则读 [`references/evaluation.md`](references/evaluation.md)。
13. **零基础步骤必须能直接照做。** 说清复制什么、粘贴到哪里、发给谁、怎样执行、看到什么算成功；不能因此增加多余的方法论和复杂工作流。
14. **换聊天不等于开始新内容。** 同一条视频继续用原来的 T 编号和最新确认状态；先找这条的草稿文件夹或最近确认稿，不让不同聊天各存一套版本。
15. **本 Skill 的规则优先于判断库里的写法。** 判断库和参考写法只作参考，不能覆盖或改写本 Skill 的硬规则和工作流；要改，走第 8 步，由用户确认。

## 教程与口播分支

用户调用时说「教程」或「口播」；没说就问一句，不猜。

| | 教程 | 观点口播 |
| --- | --- | --- |
| 叙事确认 | 第 2 步 | 第 2 步，另加两条：至少一段只有作者能说的一手证据（亲自聊过的人、亲手做过的事、亲眼看到的数字），没有这一段，再多「我觉得」也像洗稿；热点只当证据，用来证明「变化真的开始了」，主线必须回答「这跟观众有什么关系、他能得到什么」 |
| 写稿参考 | 按阶段读判断库 | 同左，写完再做一次说教味自查（见下） |
| 第 4 步画面规划 | 必做 | 不做 |
| 硬规则 13 零基础步骤 | 适用 | 不适用 |
| 事实核查 | 见下 | 同左，另加：二手材料（包括你自己的旧稿或直播提词稿）先对照原始来源查一遍，确认没有把别人的说法当成自己的、没有传错 |
| 反馈记录 | 同一份 `写稿方法/反馈记录.md` | 同一份，关联内容写明「口播」 |

**事实核查（两种都做）：** 写之前检查版本、来源、活跃度、安装方式和能力是否真实；外部数字、模型能力和产品设置用最新的一手来源核对。AI 自己电脑上装好了某个工具，不代表观众电脑上也有。核查可以严格，口播只留会影响观众理解、判断或行动的边界；事实边界靠措辞解决，不靠加一段免责声明。

**说教味自查（口播写完做）：** 观众觉得被上课，多半是说话人站在观众上方宣布标准答案。逐段看这几样：「绝对／一定／必须／真正」这类断言词是不是很多；有没有「不是……而是……」式的辩护句；全篇有没有问句、例子和「对吧」这类跟观众确认的话；判断有没有来处（从哪次经历、和谁聊过得出的）；是不是一句一段像在念格言。改法：把判断的来处说出来；先讲机会，再替观众问「那我该怎么做」；要求句前面加上前提（「如果你想……你要……」）；结尾把选择还给观众。「你要」这类词本身不是问题。

## 工作流

### 1. 写稿前准备

先找到工作文件夹，确定这条内容的 T 编号和草稿文件夹，读选题卡（有的话）。判断库、口气样本是空的，按上面说的告诉用户一次。

如果是在续接已有视频，先认出原来的 T 编号，回读最近确认的逐字稿（`工作稿.md` 或 `定稿.md`），以及标题、封面、简介和教程各自的状态；没有外部采用证据时标为「外部状态未知」，不要因为聊天里没看到确认，就反推现实中没有采用。

再核实影响叙事的三件事：

- 核心事实是否成立；
- 必要条件和关键边界是什么；
- 有没有能展示的结果、过程或对比。

涉及内容类型（工具包、真实任务工作流、结果对比）、主要收获和讲多深时，读 [`references/baseline-model.md`](references/baseline-model.md)。

有参考视频时：

1. 先看当前聊天，和这条内容草稿文件夹 `内容草稿/T001_选题名/` 里的 `参考拆解.md`。已有 `jc-video-analysis` 的拆解结果就直接复用，按下面几条核对有没有关键缺口；确实没有，再调用 `jc-video-analysis` 拆解。不自动翻别的聊天记录，也不用临时编的通用提示词代替固定的拆解方法。
2. **评论区只在用户明确要求时分析。** 只有用户本轮明确说「分析评论区」或同义的话，才调用 `jc-media-research` 的评论需求那条路。用户只给了参考视频、链接或逐字稿，或只要求拆参考、写稿，都不等于授权分析评论区：不抓取、不读取、不整理、不引用评论区，也不产生相关费用。
3. 已有拆解结果时，把它和原始素材直接当输入，先判断够不够决定用户自己的受众、承诺、证明、内容顺序和画面。
4. 只补会改变这条视频叙事或拍摄方案的关键缺口；没有关键缺口就直接进第 2 步，不重新生成一份完整参考报告。
5. 默认在完成拆解的同一个聊天里继续，方便同时看原始素材和时间码证据；用户有意另开聊天时，新聊天直接读草稿文件夹里的 `参考拆解.md`，需要核对时再按里面的原始素材路径回看。
6. 参考拆解只说明对方怎样做、为什么可能有效、哪些条件不能照搬；用户自己的判断、真实结果和制作条件仍在本 Skill 里确认。
7. **爆款开头只在用户要求时存。** 用户本轮要求、或之前明确授权过保存参考开头时，把这条参考的开头追加进 `写稿方法/爆款开头.md`（开头原句＋数据＋一句话说为什么留得住人；文件不存在就新建）；只记这一条，不批量搜集。没有授权时，只在聊天里交付这条待保存的条目，不写文件。这个文件和判断库分开，不往 `07_我的判断库.md` 里写。
8. **收到别人写的初稿（运营稿、旧稿等），第一个回复先出来源表。** 逐段写清这段来自哪条参考视频的哪一段、哪次讨论，还是原稿作者自己的判断，依据属于哪一类，建议留、改还是删；骨架选得不对先换骨架，再谈措辞。不直接在初稿上润色。
9. **出处按类型标注，引号里的原话先比对。** 每条出处标明类型：参考视频口播（带时间码）、画面、标题或发布文字、讨论记录、用户定过的、判断库里已有的、AI 自己判断的。标题和发布文字只能写「只在发布文字里，视频没说」，不算视频依据。打引号的原话发出前，先用程序在逐字稿里搜一遍，搜不到就不打引号。需要用户逐条拍板的一批修改建议：这条稿已经有创作页的，建议放进创作页；还没有创作页、又要逐条拍板的，先用 `jc-gongzuotai-write` 做成创作页。

### 2. 确认叙事框架

不要把一组问题直接抛给用户。先从参考视频里说清楚：

- 它主要讲给谁；
- 观众看完具体得到什么；
- 它用什么内容或画面让人相信；
- 它主动没讲什么。

然后结合这次的材料给出推荐方案。**前两条是生死线：答不出就不进逐字稿，先回叙事讨论。** 为了不拖慢节奏，AI 先从当前材料、选题卡、已有调研和判断库里给出候选答案让用户挑，不让用户空想；只有用户本轮明确要求分析评论区时，才能把评论里的证据当候选依据。

- **这条拍给谁：** 一群在某个特定场景下有同一个需求的人，例如「刚装好某个 AI 工具、不知道第一件事该让它干什么的人」。不用职业、年龄这类标签回答。
- **为什么这群人要看你，而不是别的博主：** 你有什么别人没有的经历、结果或角度。能说出「只有我」最简单。
- **观众现在知道多少：** 还没意识到有这个问题／知道问题／知道有解法／知道具体产品／就差一步。这决定开头第一句说什么：没意识到问题的人，开头先让他看见问题；就差一步的人，开头直接给结果或方法。
- **这条主要推观众哪一下：** 戳他现在的难受／给他看能得到的结果／拆掉他的害怕和顾虑／降低开始的门槛。一条主要推一下。
- 观众看完具体得到什么；
- 用什么事实、案例或结果证明；
- 哪些内容明确不讲；
- 作者最值得表达的判断。AI 可以根据判断库和以往内容先给候选，但必须由用户选择、修改或补充；
- 实际制作条件：目标时长、已有录屏、能不能补录、愿意花多少准备工夫，由用户最终确认。

最后直接给出叙事框架：开头原句、接下来按什么顺序讲、每部分解决什么问题。教程视频同时写明每部分准备让观众看到什么。

必要时给 2 个真正不同的方案并说明取舍；没有真实分歧时只给推荐方案。只有用户明确说「确认」「按这个来」或同义的话，才进入完整脚本。方向上的认可、继续讨论或含糊的回答都不算确认。

### 3. 分段写稿与显示修改痕迹

叙事确认后，动笔前先对口气：

- **有口气样本**（`写稿方法/08_我的口气样本.md` 里有内容）：按这条的类型读一到两条同类终稿，数据好的优先；再看「改前 → 改后」的句子。读的时候看开头前两句怎么给观众继续看的理由、段和段之间用什么口语接上、常用哪些词，不看讲了什么。参考视频里同一处的原话放在手边。句子往用户的已发布稿和参考原话靠，不往书面稿靠；写完逐句对一遍样本里的「改前」，像「改前」的先改掉再交给用户。
- **没有口气样本**：第一次写稿前，问用户要一两条他已经发出去、自己满意的同类稿（贴文字或给文件路径都行）。用户给了就按上面的读法读；没有就先按参考视频原话的口语程度写，写完提醒用户：满意的终稿可以存进 `写稿方法/08_我的口气样本.md`，下次写稿会更像他。

然后：

1. 先写开头、最需要用户判断的一段和结尾；这三段方向通过后，再补齐完整逐字稿，写进 `内容草稿/T001_选题名/工作稿.md`。
2. 用户要求修改时，输出完整的当前版本，不只发修改片段。
3. 没改的原文保持不变；删掉的内容写成 `~~原文~~`，替换内容紧跟其后写成 `**【改为：新内容】**`。
4. 每轮只改用户重新打开的部分，不顺手润色其他已确认段落。
5. 建工作稿的同一轮，在草稿文件夹里建一份 `改稿日志.md`：之后每一轮改完（AI 改或用户改），按「段号｜原句 → 新句｜谁改｜为什么」追加，一轮一节；用户没说原因时写「AI 归纳」并标出来；整段重写时只记一行「整段重写＋原因」，不逐句列。全稿快照只在叙事级别的切换时存进 `版本/`（换骨架、换叙事、定稿），不每轮存。用户最终确认后，另存一份可以直接拍的干净逐字稿 `定稿.md`，放在草稿文件夹根目录，每条只存一份；带修改痕迹的稿由改稿日志代替，用户明确要时再单独生成。
6. 只有用户明确要和参考视频比较时，才给左右对照，不设成每条的固定格式。
7. 定稿时，从改稿日志里挑出用户亲手改的句子，整理几条「改前 → 改后」给用户过目；用户逐条同意的，才追加进 `写稿方法/08_我的口气样本.md`（文件不存在就按 [`references/口气样本怎么攒.md`](references/口气样本怎么攒.md) 的格式新建）。

想让用户直接在网页上改稿时，调用 `jc-gongzuotai-write` 把工作稿做成创作页。

### 4. 规划教程画面

教程视频按一个段落或一个操作步骤说明，写进草稿文件夹的 `画面规划.md`：

- 这段口播是什么；
- 观众当时看到什么；
- 现有素材能不能支撑；
- 还需要录真人出镜、屏幕操作、结果画面，还是交给剪辑处理。

目标是让逐字稿和最终成片能配合，不是给每句话单独配一张图。纯口播视频不做这份说明。涉及关键操作、真实结果和事实证明的画面必须能落实；普通氛围画面或不影响理解的补充画面可以留给剪辑解决。

面向零基础观众的关键操作，还要同时说明：复制或输入什么、放到哪个具体位置、怎样触发执行，以及成功后会看到什么。

### 5. 分别处理标题、封面、简介和教程

逐字稿确认后，按用户当前进入的阶段分别处理，不一次全部生成：

- 这条内容有创作页时：用户在创作页上确认内容以后，标题、封面文字、简介的候选一次出齐，放进创作页，同时贴在聊天里让用户快速挑；做法见 jc-gongzuotai-write 里出标题、封面文字、简介那一步。封面图用 jincheng-workbench 仓库的封面 Skill（jincheng-workbench-cover）做，这里只出封面上的字；教程的录屏规划和教程文档仍按阶段分别处理。出之前先读判断库里关于标题、封面、简介的条目（有的话）。
- 没有创作页时：在聊天里分别出标题、封面文字的候选；简介可以交给 `jc-jianjie`。
- 每一项都以当前确认的逐字稿为准，没有改写逐字稿的权限。
- 出标题或封面文字之前，先读 `已发布/00_已发布总览.md` 最近 10 行（没有这个文件就跳过），看同类视频哪种标题和封面数据好；只带结论进创作，不整表复述，不在写稿阶段提前读。
- 每一项分别标记为候选、对话中已确认、已实际发布或外部状态未知。
- 做这些时发现事实冲突，只指出冲突、交回用户处理，不暗中改稿。
- 每个平台最多保留一个主要的后续动作。

### 6. 试读与发布前评审

最终锁稿或发布前：

1. 优先让用户真实读一遍口播；已有录音或成片时直接按真实表现检查。还没实测时做内部朗读检查，并明确标「口播未实测」，不假装已验证。
2. 读 [`references/evaluation.md`](references/evaluation.md)，检查收获、口播、事实证据、教程交付和平台承接。
3. 终审不再读判断库里新的写法候选；只输出「通过」「修改后通过」或「暂缓发布」，必须修改项最多 3 条；通过后只继续用户当前要求的发布内容，不重新打开已确认的逐字稿。结论是「暂缓发布」时，说清唯一阻断原因和解除条件，发不发由用户决定。

### 7. 记录反馈

这一步由反馈事件触发，不等锁稿、成片或发布。下面这些情况要记：

- 用户明确评价哪里好、哪里不好，并说了原因；
- 用户亲自改稿，或纠正 AI 对修改原因的误判；
- 真实试读、录制、拍摄或剪辑暴露出内容问题；
- 用户确认锁稿，或给出成片和发布数据。

纯提问、发散讨论、问进度、用户还没接受的 AI 建议，以及已有条目完整覆盖的重复表态，不记。

需要记时，AI 自动追加到工作文件夹的 `写稿方法/反馈记录.md`（不存在就新建），用户不用填。格式见 [`references/evaluation.md`](references/evaluation.md)。执行顺序：

1. 先读相关条目去重；同一反馈已经完整记过就不重复追加。
2. 如实区分用户原话、实际修改和 AI 对原因的理解；不能根据终稿反推用户不喜欢某个没采用的说法。
3. 普通修改原因按「AI 归纳」记，不在每个阶段结束时让用户逐条确认。证据冲突且不同选择会明显改变产出，或某条 AI 归纳准备写进判断库成为长期判断时，才把相关的简短清单交给用户确认；可以等、不影响当前交付的疑问集中提，已经明确确认过的不重复问。
4. AI 可以结合已有记录、同类修改和发布结果自己归纳，但必须标成「AI 归纳」并列出证据，不能写成用户原话。
5. 新反馈推翻旧分析时，追加一条校正记录，不删、不改历史反馈。
6. 写入后重新读一遍新增的位置，确认路径和内容正确。
7. 当前阶段结束或用户说「沉淀」「复盘」时，AI 把反馈分成：给判断库里已有判断补一个例子、缩小已有判断的适用范围、只留作案例、暂不沉淀、新增判断。只有「给已有判断补一个例子」（加一行证据，不改判断和适用范围）AI 可以自己写进判断库并告诉用户；新增、改说法、改适用范围、处理冲突、删除，都要用户逐条同意，写进去之前先查重，把库里原文和候选并排摆出来。只要求复盘分析、没授权写入时，只交付结论和建议。

用户本轮明确说「只在聊天里讨论」「不要写文件」或同义的话时，以这句为准，本轮不自动写入。之后用户明确说「保存」「沉淀」，或复盘请求明确允许补记时，再从这条内容的聊天和产物里补记；涉及判断库时，仍按上面第 7 条要用户同意。

### 8. 用真实内容复盘与迭代

用户说「复盘」「开始迭代」或「根据反馈迭代」时：

1. 默认直接用用户下一条真实内容验证，不要求重做已经完成的视频。
2. 记录第一版叙事框架留下了多少、有没有重复犯错、有没有推倒重写或用户亲自重写、实际耗时，以及教程画面规划是否真的帮到拍摄。
3. 一条内容只能发现明显问题，不能单独证明流程已经成熟；继续在后面的真实内容里观察。
4. 读和当前问题相关的 `写稿方法/反馈记录.md`、判断库条目和这条内容的产物，判断是已有判断的新证据、新条件、反例，还是真正的新问题。
5. 结论按第 7 步第 7 条分类；写判断库照那里的同意规则。只要求复盘分析、没授权写入时，只交付结论和建议。
6. 判断库或参考写法里的某条即使被一条内容用上，也不能自动变成本 Skill 的规则；只有在多条真实内容里重复成立、边界清楚、没有明显反例时，才提出一处精确的 Skill 修改，等用户确认后再写入（想按复盘系统地改 Skill，可以用 `jc-skill-writer`）。
7. 只在现有事实互相冲突、又没法从真实产物里解决时请用户判断；不让用户重新审已经给过的整批反馈。

## 输出风格

- 先给结论和具体例子，再给理由。
- 让用户拍板时只摆出真正需要选择的差异，不堆术语。
- 不用课程腔、参数堆砌和空泛的「效率提升」。
- 不照搬参考博主的口头禅；要学的是怎样把能力翻译成观众的收获、怎样证明、怎样把信息压短。
- 深度档位、内容类型名称和评审分类只供 AI 内部判断，不直接展示给用户；对外只说这条视频具体怎么做。
- 用户说「我还是不懂」时，停止解释术语，删掉术语，用一个真实例子重新讲清。
