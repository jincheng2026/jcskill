# 用户材料、口播和反馈

## 先找本人材料

选题推荐和写稿前，先在用户指定的项目目录、知识库入口或明确提供的 profile 路径中查找：

- 用户已经说过的观点。
- 真实使用经历。
- 可以公开的结果和数字。
- 用户对 AI 与人的分工判断。
- 已确认的语言风格和发布边界。

Skill 只规定怎么找和怎么验证，不写死某台电脑的目录。缺少非核心材料时明确标注缺口；只有继续必然编造才问一次不可替代的输入。

## 写稿最低材料

直接生成完整口播只需要两个不可替代的本人输入：

1. 这条内容真正想表达的判断。
2. 一个能公开的真实经历、操作或观察。

数字不是必填项。用户没有提供数字时就不用数字，不得为了增强说服力追问或编造。用户在当前消息、前文或指定资料中已经给出上述两项，就视为材料足够，直接写完整口播。

「刚才找到的选题、评论需求和爆款结构」指本次对话已经取得的研究材料。直接复用，不让用户再次粘贴、选择或确认。只有两项本人输入都不存在，且用户明确要求写成带本人表达的可发布稿时，才询问一个合并问题：请用户用一句话说出一个真实经历，以及他真正想表达的判断。若只有非关键细节缺失，使用不带虚构事实的表达完成稿件，或在局部标 `[待补]`，不把它变成新的聊天轮次。

## 从参考到自己的内容

可以借鉴：

- 问题出现的顺序。
- 信息密度和证明方式。
- 用户容易卡住的具体环节。

不能直接借鉴：

- 对方的个人经历和结果。
- 未验证的比例、时间、收入和后台数据。
- 只有对方身份成立时才成立的承诺。
- 原句、独特表达和完整叙事结构的复制。

先写「参考证据告诉我们什么」，再写「用户本人怎么看」，最后才形成口播。

## 共同写稿

默认一次完成：

1. 复用本次对话已有的选题、评论和结构证据。
2. 用户没有指定选题时，自动采用当前证据中最值得拍的一条，并用一句话交代选择依据，不让用户先选。
3. 从本人材料中提取一个核心判断和一个真实经历／观察。
4. 在后台形成写作卡：目标观众、唯一主要收获、可信证据、用户判断、已有画面、禁说内容。不要把这张卡发给用户确认。
5. 按「真实需求 → 新可能 → 简单做法 → 可见结果／可信证据 → 用户判断」组织内容。功能很多时也只保留一条主要收获，其余功能用于证明，不按研究步骤机械报菜名。
6. 直接交付完整口播；不要先发提纲、确认卡、风格选项，也不要询问时长、平台或是否继续。
7. 正文之后只附极短的「画面落点」和「材料对应」；每个主要段落对应一个真实可取得的画面或证据。
8. 用户说「确定」「确认」「就这个」后固定文字，直接执行后续步骤。
9. 用户说「锁稿」「不要改」后，未经明确授权不再改写。

不要为了像爆款而加入用户没说过的夸张数字、虚假冲突或万能承诺。

## 口播质量硬门

交付前静默读一遍并自行修改，不增加用户轮次：

1. 收获：看完后，普通观众得到一个什么具体新能力、判断或结果？只能有一个主要答案。
2. 开头：第一句话是否直接给冲突、结果或新可能，而不是泛泛说「今天分享」？
3. 口语：删掉论文句、报告句、连续名词堆叠和没人会自然说出口的表达。
4. 事实：每个数字、时间、效果和第一人称经历都能回到本人材料或证据；对标账号的数据不能移植给用户。
5. 画面：每段都能落到真人、屏幕操作、结果画面或证据截图之一；没有画面就删掉装饰性描述。
6. 密度：每段必须增加新的理解、入口、做法、结果或判断；重复解释、空泛过渡和防御性说明直接删除。

没有平台和转化目标时，不自动添加「点赞、收藏、关注」等通用 CTA。结尾优先使用用户真实判断；用户明确要求行动引导时，只保留一个下一步。

## 记录本次反馈

在任务目录保存 JSONL，每行至少包括：

```json
{
  "task_id": "example-task",
  "artifact": "script",
  "decision": "accept|reject|edit|freeze",
  "reason": "用户原话或准确转述",
  "changed_part": "发生变化的具体部分",
  "recorded_at": "ISO-8601"
}
```

一次接受、拒绝或修改只标为单次观察。至少两个独立任务出现相同原因后，才建议形成长期偏好；建议不是自动写入，必须由用户确认。

## 交付检查

- 每个数字都能回到本人材料或公开证据。
- 用户经历没有从参考博主身上移植。
- 结构分析有逐字稿支持。
- 用户观点和 AI 推断分开。
- 口播长度按实际文字或试读计算，不凭感觉写时长。
- 口播不是研究报告的口语摘要，且每个主要段落都有真实画面落点。
- 未经本人材料支持，没有「我花了半天」「节省 80% 时间」等第一人称数字，也没有把对标表现写成本人效果。
- 最终状态是候选、已确认还是已锁定，写清楚。

## 三种写稿入口

- 真实任务：从用户确实做过的操作、遇到的困难与判断起稿，把研究作为证明或补充。
- 对标改写：先决定借用的逻辑，再用本人的任务、案例和判断重建表达。
- 局部修改：只改用户指出的部分，保留其他已确认或锁定文字；修改后回看前后承接。

每段记录 references、borrowed_logic、own_facts、expression_change、material_gap。references 与 own_facts 都用能回到原文的 source_id、paragraph_id、quote。本人材料也是来源；原稿中的第一人称不自动成为用户事实。

语义与写作由 Agent 直接依据材料完成。用含义相反的本人观点作检查时，分析结论、例子和稿件必须相应改变；不能保留固定话术只替换产品名。

## 通用写稿页的数据与保存

state.json 为任务状态真源，包含 schema_version: 2、task_id、title、revision、sources、sections、history。sources 原文只读；每段包含 id、title、mine、note、locked、references、semantic_groups、reviewed_text、analysis_status 和 history。

先按 data-contract.md 创建 state.json，再运行 research_decisions.py render-writing。无服务时可在浏览器暂存并下载稿件、完整页面和 JSON，浏览器暂存不是原文件写入。服务模式运行 serve_workbench.py --task-dir TASK/writing；GET /api/state 读取，POST /api/save 仅接受 revision 和各段的 id、mine、note，来源和 locked 段不允许通过保存接口修改。

保存先核对 revision；冲突返回 409，页面保留未保存输入。成功写入前一版历史、递增版本，原子替换 state.json 后更新 writing.html。HTML 更新失败时内容仍在状态文件，报告失败会明确显示，重启服务可以重建。连续编辑时保存响应不能丢掉请求期间的新输入。

改稿后重算连续汉字和数字重合，忽略标点、空格和英文产品名，默认至少 8 字；这不是全文相似率。reviewed_text 与当前文字不同则语义分析待复核。Agent 回读当前稿和引用、更新对应 semantic_groups 与 reviewed_text 后才能标 reviewed。批注变更不使文字分析失效。

import-t016 从旧页面复制三条来源、分段、我的稿子、批注、旧基线、原稿变更历史、20 组标注及复核历史，原始页面保持只读。通用页面不是新的正式稿件状态库，是否采用导出的稿件仍由用户判断。
